## 1. 全体構成

1つのNode.jsプロセスの中に、Web UIの配信、API、撮影ジョブの実行がまとまっている構成にする。
利用者は自分だけなので、プロセスを分けたり外部のキュー（Redisなど）を使ったりはしない。

```
┌──────────── ブラウザ（利用者の画面） ────────────┐
│  Web UI（React）  http://127.0.0.1:4310          │
└───────┬──────────────────────────▲──────────────┘
        │ REST API                 │ 進捗の通知（SSE）
┌───────▼──────────────────────────┴──────────────┐
│  Node.js サーバー（Fastify）                     │
│                                                  │
│  ┌─ API層 ──────────────────────────────────┐   │
│  │ 撮影 / 履歴 / 比較 / ログイン / サイト設定 │   │
│  └───────────┬──────────────────────────────┘   │
│  ┌───────────▼──────────┐  ┌─────────────────┐  │
│  │ ジョブ管理            │  │ イベント配信     │  │
│  │（撮影セッションの実行）│─▶│（進捗をSSEへ）   │  │
│  └───────────┬──────────┘  └─────────────────┘  │
│  ┌───────────▼──────────────────────────────┐   │
│  │ クローラー（URLの収集・重複除外・範囲判定）│   │
│  ├──────────────────────────────────────────┤   │
│  │ 撮影エンジン（表示完了の判定・スクロール・ │   │
│  │ 撮影・画像の結合）                         │   │
│  └───────────┬──────────────────────────────┘   │
│              │ Playwright                        │
│  ┌───────────▼──────────┐  ┌─────────────────┐  │
│  │ Chromium（画面なし）  │  │ SQLite / 画像    │  │
│  └──────────────────────┘  └─────────────────┘  │
└──────────────────────────────────────────────────┘
```

- サーバーは `127.0.0.1` だけで待ち受ける（ほかのPCからは接続できない）
- ポート番号は `4310`。ほかのアプリとぶつかる場合に備え、環境変数 `PORT` で変えられるようにする
- ログイン用のブラウザだけは画面ありで起動する（7章）

### 1.1 起動方法

ターミナルで次を実行する。サーバーが起動すると、既定のブラウザで `http://127.0.0.1:4310` を自動で開く。

```
pnpm start
```

- `pnpm start` は画面（packages/web）をビルドしてからサーバーを起動する。開発中は `pnpm dev` で、サーバー（4310）と Vite（5173、画面の変更をすぐ反映）を同時に起動する
- 止めるときはターミナルで `Ctrl + C` を押す。撮影中のページを撮り終えてから終了する（もう一度押すとすぐ終了）。それでも途中で止まった撮影セッションは、次の起動時に `stopped` として扱う
- 自動でブラウザを開かないようにするには、環境変数 `NO_OPEN=1` を付ける
- 常に裏で動かしておく仕組み（Macのログイン時の自動起動など）は作らない
- 初回だけ `pnpm install` と `pnpm exec playwright install chromium` が必要。手順は README に書く

## 2. 技術選定

| 用途 | 採用 | 理由 |
|---|---|---|
| 実行環境 | Node.js 24（LTS）＋ TypeScript | Playwrightを使うため。画面側と言語をそろえられる |
| ブラウザ操作 | Playwright（Chromium） | フルページ撮影、画面幅の指定、ログイン状態の保存（storageState）が標準でできる |
| サーバー | Fastify | 軽く、静的ファイルの配信とSSEを簡単に書ける |
| データベース | SQLite（better-sqlite3） | ファイル1つで済み、別にインストールするものがない |
| 画像処理 | sharp | 分割撮影した画像の結合（J-05）とサムネイル作成 |
| ZIP書き出し | archiver | V-06 |
| 画面 | React ＋ Vite ＋ React Router | 一覧・比較画面のように状態の多い画面を作りやすい |
| パッケージ管理 | pnpm（ワークスペース） | サーバーと画面を1つのリポジトリで管理する |

## 4. データモデル

```
crawls（撮影セッション）
  id, start_url, status, settings_json, auth_profile_id, output_dir,
  created_at, started_at, finished_at,
  pages_found, pages_done, pages_failed, pages_skipped, error_message

pages（ページ）
  id, crawl_id, url, normalized_url, path, group_key, depth, found_from_page_id,
  status, skip_reason, http_status, title, final_url, error_message, wait_timed_out,
  created_at, updated_at
  ※ (crawl_id, normalized_url) で一意

shots（画像）
  id, page_id, viewport_width, file_path, thumb_path,
  image_width, image_height, method, fell_back, captured_at
  ※ (page_id, viewport_width) で一意

auth_profiles（ログイン状態）
  id, name, origin, storage_state_path, created_at, last_used_at

site_settings（サイト設定・プリセット）
  id, name, host_pattern, is_builtin, settings_json
```

- `status`（crawls）: `queued` → `running` → `done` ／ `stopped` ／ `error`
- `status`（pages）: `queued` → `capturing` → `done` ／ `failed` ／ `skipped`
- `skip_reason`（pages）: `robots`（robots.txt で禁止）、`sampling`（間引き）、`max-pages`（最大ページ数を超えた）、`not-html`（HTML以外）
  - 範囲外のリンク（外部サイト、除外パターン、HTML以外の拡張子、最大階層より深い）は記録しない。外部サイトへのリンクまで記録すると件数が膨れるため
- `method`（shots）: 撮影方式（`fullpage`、`tiled`、`expand`、`stitch`）。`fell_back` は展開方式からつなぎ合わせ方式に切り替えたかどうか
- 実装は `packages/server/src/db/`（better-sqlite3）。スキーマの版は `PRAGMA user_version` で管理する
- `group_key`: 同じ階層のページをまとめるためのキー（5.3）
- `settings_json`（crawls）: 撮影開始時の設定をまるごと保存する。あとで同じ設定で撮り直せるようにするため

## 5. クローラー

### 5.1 処理の流れ

```
起点URL ─▶ robots.txt と sitemap.xml を読む ─▶ キューに入れる
                                                  │
        ┌─────────────────────────────────────────┘
        ▼
  キューから1件取り出す（同時に concurrency 件まで、間隔 intervalMs）
        │
        ├─ 最大ページ数に達した ─▶ 残りは skipped にして終了
        ▼
  撮影エンジンで1件目の画面幅を表示（6章）
        │
        ├─ 表示したページからリンクを集める（5.4）
        │     └─ 正規化 → 範囲判定 → 重複判定 → 間引き判定 → キューへ
        ▼
  すべての画面幅で撮影 ─▶ 結果を保存 ─▶ 進捗イベントを送る
```

リンク集めは、選ばれた画面幅のうちいちばん広い幅（初期値 1440px）で表示したときだけ行う。スマホ幅でしか出てこないページがあるサイトは撮る予定がないため、ほかの幅ではリンクを集めない（11章 #4）。

M2 で決めた細かい点:

- 起点URLの次に、サイトマップのURLをキューに入れる。サイトマップから来たページの階層は 1 とする
- robots.txt に `Crawl-delay` があり、`respectRobotsTxt` が true なら、アクセス間隔をその秒数以上にする
- サイト設定（プリセット）の `concurrency`・`intervalMs` は、アクセスを控えめにする方向にだけ効かせる（同時に開くページ数は小さいほう、間隔は大きいほうを使う）
- 転送された先が範囲外（外部サイト）だった場合、そのページのリンクはたどらない
- 途中で止めたとき、撮影中のページは撮り終えてから止まる。アクセス制限で待っている間でも、待ちを打ち切ってすぐ止まる。撮っていないページは `queued` のまま残す
- 実装は `packages/server/src/crawler/`（判定の部品）と `packages/server/src/jobs/crawl-runner.ts`（実行）。コマンド `pnpm crawl <URL>` で動かせる

### 5.2 URLの正規化（C-03, C-03a）

1. `#` 以降を削除する
2. ホスト名を小文字にし、既定のポート（`:443`、`:80`）を削除する
3. `keepQueryParams` が false ならクエリを削除する。true ならクエリをキー名で並べ替える。どちらの場合も `utm_*`、`fbclid`、`gclid` は削除する
4. パスの末尾の `/` をそろえる（`/about` と `/about/` は同じページとみなす）。`index.html` も削除する
5. 正規化したURLを `normalized_url` として、撮影セッションの中で一意にする

### 5.3 範囲判定と間引き

範囲判定（上から順に判定し、外れたら捨てる）:

1. スキームが `http` か `https`
2. ホストが起点と同じ。`includeSubdomains` が true なら、起点の登録ドメイン（例: `example.com`）の配下も可
3. 除外パターン（`excludePatterns`）に当てはまらない。初期値は `logout`、`signout`、`sign-out`、`delete`、`destroy`
4. 拡張子が明らかにHTML以外（`.pdf`、`.jpg`、`.zip` など）ではない
5. `respectRobotsTxt` が true なら、robots.txt で禁止されていない
6. 階層が `maxDepth` 以下

HTML以外かどうかは、実際に開いたときの `Content-Type` でも確かめる。HTMLでなければ `skipped` にする（C-10）。PDF などブラウザがダウンロードとして扱うものも同じ扱いにする。

重複の判定には正規化したURLを使うが、実際に開くのは元のURL（`#` 以降と、`keepQueryParams` が false ならクエリを除いたもの）とする。`/about/` を `/about` に変えて開くと 404 を返すサーバーがあるため。

判定の順番は「範囲 → 最大階層 → 重複 → robots.txt → 最大ページ数 → 間引き」。

間引き（C-03b）:

- `group_key` は「パスの最後の区切りを除いた部分」とする（例: `/blog/2026/hello` → `/blog/2026/`）
- `firstN` を選んだ場合、同じ `group_key` のページは見つけた順に N 件まで撮り、それ以降は `skipped`（理由: 間引き）にする
- 対象の階層は `prefixes` で指定する（例: `['/blog/', '/products/']`）。`'auto'` の場合は、トップ直下（`group_key` が `/`）以外のすべての階層を対象にする
  - トップ直下を対象外にするのは、`/about`、`/company`、`/contact` のように、型の違うページが並ぶことが多いため

### 5.4 リンクの集め方（C-08, J-06）

- 1つ目（いちばん広い）の画面幅を撮り終えた後に、`a[href]` をすべて集める。`<area href>` も対象にする。末尾までスクロールした後に集めるのは、スクロールして初めて描画されるリンク（フッターなど）も拾うため
- 制約: 描画が落ち着いたと判定した後（6.2、初期値では最後の変化から1秒後）にさらに遅れて追加されるリンクは拾えない
- ページ移動のJavaScript（`history.pushState`、`history.replaceState`）をページ読み込み時に横取りする小さなスクリプトを入れておき、表示中に発生したURLも集める
- `onclick` だけで移動するボタン（`href` がない要素）はたどらない（要件の対象外「ボタン操作をしないと出てこないページ」に当たる）

## 6. 撮影エンジン

### 5.5 アクセス制限への対応（M0 で追加）

M0 で、Notion は10秒間隔の読み込みでも制限をかけてくることが分かった（[m0-findings.md](m0-findings.md) 3.1）。制限には次の2種類がある。

- **はっきりした制限**: ページ本体が 429・403 を返す、またはロボット確認画面（Cloudflare など）が出る
- **見えにくい制限**: ページ本体は 200 で返るが、裏の API が 429 を返し、画面の一部が描画されない

対応:

1. 撮影中の通信を監視し、ページ本体または読み込み中の通信に 429 が1件でもあれば「制限された」とみなす。ロボット確認画面は、ページのタイトルと Cloudflare の確認用要素で見分ける（`capture/blocked.ts`）
2. 制限された撮影は成功扱いにせず、その画像は保存しない
3. そのホストへのアクセスを止め、`Retry-After` ヘッダーの秒数、なければ 60秒 → 120秒 → 240秒 待ってから撮り直す。3回失敗したら、そのページは `failed`（理由: アクセス制限）にして次へ進む
4. 制限を検出したホストは、その撮影セッションの間、アクセス間隔を2倍にする
5. ロボット確認は突破しない。出た場合は、待つか、ログイン用ブラウザ（7章）で利用者自身が確認を済ませたログイン状態を使うよう、画面で案内する
6. 待っている間は、進捗画面に「アクセス制限のため 120秒待機中」のように表示する（進捗イベント `warning`）

## 6. 撮影エンジン

### 6.1 1ページを撮る手順

```
① 新しいタブを開く（ログイン状態・Basic認証は撮影セッション単位のブラウザコンテキストに設定済み）
② 画面幅を設定してURLを開く（DOMの読み込み完了まで待つ）。ステータスコードを記録
③ 隠す要素とアニメーション停止のCSSを差し込む（S-05, S-06）
④ 指定要素の表示を待つ（J-02）
⑤ 描画が落ち着くのを待つ（J-01, 6.2）
⑥ 撮影前スクリプトを実行する（J-07, J-09）→ もう一度 ⑤
⑦ スクロール領域を見つける（J-03, 6.3）
⑧ 末尾までスクロールして中身を描画させ、先頭に戻す（J-04, S-04）→ もう一度 ⑤（短め）
⑨ extraWaitMs 待つ
⑩ 撮影する（6.4）→ サムネイルを作る
⑪ タブを閉じる
```

- 原則として画面幅ごとにページを開き直す。同じタブで幅だけ変えると、読み込み時に幅を見て組み立てるサイトで表示が崩れるため
- ただし、アクセス制限の厳しいサイト（サイト設定 `reloadPerViewport: false`、Notion 用プリセットなど）では、1回だけ読み込み、画面幅を切り替えながら撮る。展開方式などでページを書き換えるので、撮るたびに書き換え（差し込んだスタイルと目印の属性）を元に戻し、幅を変えてから ⑤ 以降をやり直す。M1 で実装し、検証用ページ（内側スクロール、仮想スクロール）で開き直した場合と同じ高さの画像になることをテストで確かめた
- 1ページの撮影全体に `pageTimeoutMs`（初期値 30秒）の上限を設ける。超えたら `failed` にして次へ進む（S-07）

### 6.2 描画が落ち着いたかの判定（J-01）

次の4つがすべてそろったら「落ち着いた」とする。

| 条件 | 方法 |
|---|---|
| 通信が止まった | Playwrightのリクエストイベントで、実行中のリクエスト数を数える。0件（長時間つながったままの通信は除く）が `quietWindowMs` 続いたら満たす |
| 画面の変化が止まった | ページ内に `MutationObserver` を入れ、DOMの変化が `quietWindowMs` 起きなかったら満たす |
| フォントの読み込みが終わった | `document.fonts.ready` |
| 画像の読み込みが終わった | 表示中の `<img>` がすべて `complete` |

`maxWaitMs`（初期値 15秒）を過ぎても満たさない場合は、その時点で撮って `wait_timed_out` を記録する。
WebSocketやポーリングで通信が止まらないサイトがあるため、通信の条件では次の通信を数えない。

- WebSocket と EventSource
- 5秒以上つながったままの通信（Notion の `wasm-sqlite-shared-worker` などが当たる）
- 同じ通信が3回を超えたもの（定期的な通信）。「同じ通信」は、メソッド、クエリを除いたURL、送信内容（POST の本文）がすべて同じものとする。URLだけで判定すると、1つの API のURLへ中身の違う POST を何度も送るサイト（Notion）で、読み込み途中の通信まで無視してしまう（M0 で発生）

DOM の変化も、同じ要素が5回を超えて変化した場合はその要素を無視する（時計やカルーセル対策）。

### 6.3 スクロール領域の検出（J-03）

1. サイト設定に `scrollContainerSelector` があれば、それを使う
2. なければ、ページ内の要素から次の条件に当てはまるものを探す
   - CSSの `overflow-y` が `auto` か `scroll`
   - 中身の高さ（`scrollHeight`）が表示されている高さ（`clientHeight`）より大きい
   - 表示されている面積が画面の半分以上
3. 当てはまる要素のうち、隠れている部分（`scrollHeight - clientHeight`）がいちばん大きいものを選ぶ
4. ページ全体のスクロール量のほうが大きい、または当てはまる要素がなければ、ページ全体（通常のページ）として扱う

### 6.4 撮影方式

| ページの種類 | 方式 |
|---|---|
| 通常のページ（高さ 15,000px 以下） | Playwright のフルページ撮影。横幅は画面幅で切り取る |
| 通常のページ（高さ 15,000px 超、J-05） | 画面の高さごとに位置を指定して分割撮影し、sharp で1枚に結合する |
| ページ内の一部だけがスクロールするページ | 下の「展開方式」を試し、失敗したら「つなぎ合わせ方式」に切り替える |

**展開方式**（第1候補）: スクロール領域とその親要素の高さの制限を外して（`height: auto`、`overflow: visible`）、中身を全部表示させてから、フルページ撮影する。

- 展開後に `resize` と `scroll` のイベントを送る。仮想スクロールのように、表示の高さを見て描画する仕組みに全体を描画させるため（M0 で、これがないと最初の数十行しか写らないことを確認）
- 展開後のページの高さが、スクロール領域の `scrollHeight` 程度まで伸びたかを確かめ、伸びていなければ失敗とする
- 高さの制限を外すと横にはみ出していた要素も表示範囲に入るので、画像の横幅は画面幅で切り取る（M0 で、Notion の画像幅が 2160px になったため）

**つなぎ合わせ方式**（予備）: スクロール領域を表示の高さずつスクロールしながら、その領域の部分だけを撮り、sharp でつなげる。

- 画面上部に固定されたヘッダーが何度も写り込まないよう、2枚目以降は固定要素を一時的に隠す
- 画面に入った部分しか描画しないページでも、撮る瞬間には描画されているので確実に写る

どちらの方式で撮ったかは記録し、画像の一覧で分かるようにする。

> M0 の結果: 検証用ページ4種と Notion の公開ページ（PC幅・スマホ幅）で、両方式とも末尾まで正しく写った。展開方式のほうが速い（1ページ・1画面幅で約5〜8秒。つなぎ合わせ方式は約7〜15秒）ので、この順番で確定する。

### 6.5 Notion用プリセット（J-08, J-09）

組み込みのサイト設定として用意する。`host_pattern` は `*.notion.site`。

| 項目 | 内容 |
|---|---|
| 表示完了を判断する要素 | 指定しない（6.2 の判定で、PC幅・スマホ幅とも約5〜6秒で成立した） |
| スクロール領域 | 指定しない（自動検出で本文の領域が見つかった） |
| 隠す要素（`hideByText`） | 「Get Notion free」「Notionを今すぐ使う」「Try Notion」「Notionを試す」。文字列が一致する要素を含むボタンごと隠す |
| トグルを開くスクリプト（`expandTogglesScript`） | `expandToggles` が true のとき、`[data-block-id]` の中の `role="button"` かつ `aria-expanded="false"` の要素を押す。ポップアップを開くボタン（`aria-haspopup` 付き）は押さない。入れ子のトグルのため最大5回繰り返す |
| 同時に開くページ数・間隔 | 1ページ、30秒（5.5）。M2 で、この設定で公開ハンドブックを5ページ続けて巡回し、制限を受けずに撮れることを確かめた（1ページあたり約28秒） |
| 画面幅ごとに開き直すか | 開き直さない（`reloadPerViewport: false`、5.5） |

- Notion のクラス名は `x87ps6o x1ypdohk ...` のような自動生成の名前で、変わりうる。プリセットではクラス名を使わず、要素の文字列や自動検出に頼る
- Notionの画面の作りが変わったときに直しやすいよう、プリセットはコードと分けた設定ファイル（`presets/notion.json`）に置く
- M0 で、同じ設定でもボタンの表示言語が日本語の回と英語の回があった。M1 で `Accept-Language: ja-JP` を明示しても英語で表示されたため、Notion 側で決めていると判断した。こちらでは制御できないので、比較画面（M5）では「Notion の画面部品の言語が違う場合がある」ことを前提にする

## 7. ログイン（L-01〜L-04）

### 7.1 ログイン状態の保存

```
[画面] 「ログイン用ブラウザを開く」（URLと名前を入力）
   │
   ▼
[サーバー] 画面ありのChromiumを起動し、入力されたURLを開く
   │
   ▼
[利用者] 開いたブラウザで、手でログインする
   │
   ▼
[画面] 「ログイン状態を保存」ボタン
   │
   ▼
[サーバー] ブラウザのCookieとlocalStorageを storageState として
          ~/SiteCapture/auth/<ID>.json に保存（権限 0600）→ ブラウザを閉じる
```

- アプリはパスワードを入力も保存もしない（L-02）
- `auth` フォルダは本人だけが開ける権限（0700）、ファイルは本人だけが読み書きできる権限（0600）にする。ファイルの中身は API から返さない
- 利用者がログイン用ブラウザのウィンドウを閉じたら、そのセッションは保存できない。画面は 1.5 秒ごとに状態を確かめ、閉じられたことを知らせる
- 撮影開始の画面で、ログイン状態を選ぶ。起点URLのオリジン（例: `https://example.com`）と一致するものを自動で選ぶ。利用者が自分で選んだ後は自動では変えない
- 撮影の途中でログインが切れていることに気づけるよう、起点ページを開いたときにログイン画面へ転送されたら警告を出す。転送先のパスに `login`・`log-in`・`signin`・`sign-in`・`auth` を含み、元のURLには含まないときに警告する
  - 警告は進捗の通知（SSE）で送り、撮影結果の画面に表示する。データベースには残さないので、画面を開き直すと消える
- 実装は `packages/server/src/auth/login-sessions.ts`。動作確認でウィンドウを出したくないときは、環境変数 `SITE_CAPTURE_LOGIN_HEADLESS=1` で画面なしのブラウザにできる（ログイン操作はできなくなる）

### 7.2 Basic認証（L-04）

撮影開始の画面の「ログイン」欄（折りたたみ）でIDとパスワードを入力する。設計当初は「詳細設定」に置く予定だったが、ログイン状態の選択と並べたほうが探しやすいため移した。

- Playwright のブラウザコンテキストの `httpCredentials` に渡し、撮影の間だけメモリに置く。API では撮影設定とは別の項目（`basicAuth`）で受け取り、`settings_json` には入れない
- ID とパスワードは起点URLと同じオリジンにだけ送る（`httpCredentials.origin`）。外部サイトへの通信に送らないため。サブドメインを巡回する設定でも、ほかのサブドメインには送らない

## 8. API

すべて `/api` から始まる。入出力はJSON（型は `packages/shared`）。M3 で実装したものに「済」を付けた。それ以外は M4〜M6 で作る。

- `Host` ヘッダーが `127.0.0.1:4310` か `localhost:4310` でない要求は 403 で断る。悪意のあるサイトが DNS を書き換えてこの API を呼ぶ攻撃（DNS リバインディング）を防ぐため
- 撮影設定の誤りは 400 と日本語のメッセージ（`{ error: "..." }`）で返す

| メソッド | パス | 内容 |
|---|---|---|
| POST | `/crawls` | 済。撮影を始める（本文: `CrawlSettings` の一部と、保存しない `basicAuth`。省いた項目は初期値） |
| GET | `/crawls` | 済。撮影履歴の一覧 |
| GET | `/crawls/:id` | 済。撮影セッションの詳細と集計 |
| GET | `/crawls/:id/pages` | 済。ページと画像の一覧（ツリー表示用に `path` を含む） |
| GET | `/crawls/:id/events` | 済。進捗の通知（SSE） |
| POST | `/crawls/:id/stop` | 済。途中で止める（V-01）。実行中でなければ 409 |
| POST | `/crawls/:id/retry` | 失敗したページだけ撮り直す（S-08） |
| POST | `/crawls/:id/recapture` | 同じ設定で新しく撮り直す |
| DELETE | `/crawls/:id` | 済。撮影セッションと画像を削除する。撮影中は 409。画像のフォルダは `~/SiteCapture/captures` の中にある場合だけ消す |
| GET | `/crawls/:id/export.zip` | 画像をZIPで書き出す（V-06） |
| GET | `/crawls/:id/export.csv` | ページ一覧をCSVで書き出す（V-07） |
| GET | `/compare?a=:id&b=:id` | 2つの撮影セッションのページの対応表（V-05b） |
| GET | `/shots/:id/image`、`/shots/:id/thumb` | 済。画像とサムネイルの配信。ファイルパスではなく画像の ID で指定させる（設計当初の `/files/*` から変更） |
| GET | `/auth-profiles` | 済。ログイン状態の一覧 |
| DELETE | `/auth-profiles/:id` | 済。ログイン状態を削除する（ファイルも消す） |

| DELETE | `/auth-profiles/sessions/:sid` | 済。保存せずにログイン用ブラウザを閉じる |
| POST | `/auth-profiles/sessions/:sid/save` | 済。ログイン状態を保存してブラウザを閉じる |
| GET/POST/PUT/DELETE | `/site-settings` | サイト設定・プリセットの管理（GET は済） |
| GET | `/site-settings/match?url=` | 済。URL に合うサイト設定を返す（撮影開始画面での表示用） |

### 8.1 進捗イベント（SSE）

```ts
type CrawlEvent =
  | { type: 'page-found'; pageId: string; url: string }
  | { type: 'page-started'; pageId: string }
  | { type: 'shot-done'; pageId: string; width: number; thumbUrl: string }
  | { type: 'page-done'; pageId: string; waitTimedOut: boolean }
  | { type: 'page-failed'; pageId: string; error: string }
  | { type: 'page-skipped'; pageId: string; reason: 'out-of-scope' | 'not-html' | 'sampling' | 'max-pages' }
  | { type: 'crawl-finished'; status: 'done' | 'stopped' | 'error' }
  | { type: 'warning'; message: string };           // ログイン切れなど
```

画面を開き直しても続きから表示できるよう、SSEにつないだ直後に現在の集計をまとめて送る（`{ type: 'snapshot', crawl }`）。撮影が終わったときにも最新の集計を送る。

画面側は、ページに関するイベントが届いたら 0.5 秒まとめてからページ一覧と集計を読み直す。数十〜数百ページの規模なら、イベントごとに差分を当てるより単純で十分速い。

## 9. 画面

### 9.1 画面一覧と遷移

```
撮影履歴（トップ）──▶ 撮影開始 ──▶ 撮影結果（撮影中は進捗も表示）──▶ ページ詳細
     │                                       │
     ├──▶ 比較（2つの撮影セッションを選択）◀──┘
     └──▶ 設定（ログイン状態 / サイト設定 / 保存先）
```

| 画面 | 主な内容 | 要件 |
|---|---|---|
| 撮影履歴 | 撮影セッションのカード一覧（サイト名、日時、ページ数、代表サムネイル、状態）。2つ選んで「比較」 | V-04 |
| 撮影開始 | URL、画面幅（チップで追加・削除）、ログイン状態、毎回選ぶ3つの設定（サブドメイン・パラメータ・間引き）。その他は「詳細設定」に折りたたむ。URLを入れると、合うサイト設定（Notionなど）を自動で選ぶ | C-02〜C-11, S-02, L-01, J-08 |
| 撮影結果 | 上部に進捗（見つけた数、撮影済み、失敗、停止ボタン）。左にURLの階層ツリー、右にサムネイルの格子。画面幅の切り替え。失敗・待ちきれずに撮影・間引きのフィルター。「失敗だけ撮り直す」「ZIP」「CSV」 | V-01〜V-03, S-07, S-08, V-06, V-07 |
| ページ詳細 | 原寸表示（拡大縮小）。画面幅の切り替え。URL、タイトル、ステータスコード、撮影方式、エラー内容 | V-03 |
| 比較 | 左にページの対応表（両方にある／Aだけ＝削除／Bだけ＝追加）。右にビューア。表示モードは「左右に並べる」「半透明で重ねる」「スライダー」の3つ | V-05, V-05a, V-05b |
| 設定 | ログイン状態の一覧（作成・削除）、サイト設定の編集、保存先 | L-03, J-02, J-03, J-07 |

### 9.2 見た目の方針

社内のデザインシステムは使わず、シンプルな独自のスタイルにする。

- 主役はスクリーンショットなので、画面の枠や部品は無彩色で控えめにする。色はリンク・選択中・状態（失敗、待ちきれずに撮影、追加、削除）を示すところだけに使う
- ライトモードとダークモードの両方に対応する（OSの設定に合わせる）
- スタイルはCSS変数で色・余白・文字サイズを定義し、CSS Modulesで部品ごとに書く。UIライブラリは入れない
- 文字は OS 標準のフォント（`system-ui`、日本語はヒラギノ角ゴシック）を使う

### 9.3 M3 で決めた画面の細かい点

- 撮影結果の絞り込みは「すべて／撮影済み／失敗／待ちきれず／対象外」。対象外のページは「対象外」を選んだときだけ表示する（通常は件数が多く邪魔になるため）
- 左の階層ツリーで選んだパスの配下だけを表示する。クエリ付きのページは同じパスの下にまとめる
- ページ詳細では ← → キーで前後のページへ移れる（順番は見つけた順）
- 撮影履歴は、撮影中のものがあっても件数が分かるよう、5秒ごとに読み直す
- 狭い画面（860px 未満）では、階層ツリーをサムネイルの上に置く

### 9.4 比較ビューアの仕様

- **左右に並べる**: 2枚を同じ倍率で並べる。どちらかをスクロールすると、もう片方も同じ位置（上からの距離）にスクロールする
- **半透明で重ねる**: Bの上にAを重ね、Aの透明度をスライダーで変える（0〜100%）
- **スライダー**: 2枚を重ね、左右に動かせる境目の左側にA、右側にBを表示する
- 2枚の高さが違う場合は上端をそろえ、足りない部分は市松模様で示す
- 比べられるのは同じ画面幅の画像どうしとする（画面幅の切り替えは比較画面全体で1つ）
